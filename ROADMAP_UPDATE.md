## Document Purpose

This document is a **supplemental roadmap** to the original `ROADMAP.md`.

All milestones in the main roadmap through **M14** are considered complete.  
The application is already functional and in active use.

This update focuses on the next major improvement phase:

1. Replacing agent-generated animal icons/sprites with **manually created pixel-art assets**
2. Supporting **sprite-sheet slicing** and state/animation extraction from owner-created art
3. Guaranteeing **zero pixel-loss / zero blur / zero unintended filtering**
4. Making movement depend on the **actual current Dock size**, not a hardcoded/default Dock region
5. Driving runtime resource usage down as far as possible with a strict optimization target
6. Keeping the system **native, lightweight, and maintainable**

---

## Context

The current app already works well, but the existing animal icons were generated by an agent and are not at the desired art quality level.

The project owner will create final pixel-art animal assets manually (for example in PixelLab or similar tools).  
These manually created sprites will become the source of truth for runtime rendering.

The application must support:

- Owner-provided custom pixel-art pets
- Potentially large sprite sheets (example: many cat frames in one sheet)
- Automatic slicing of frames if needed
- Clean mapping from frames to animations/states
- No pixel degradation at any stage
- Very low CPU / GPU / RAM usage from launch to quit
- Dynamic Dock-aware movement based on the real Dock geometry and size

---

## Non-Negotiable Constraints

### Visual Fidelity
- No blur
- No bilinear filtering
- No fractional sprite scaling
- No color bleed between atlas cells
- No alpha fringe artifacts
- No smoothing during resize
- No unexpected color-space conversion that changes the look of the art
- Source pixel shapes must remain visually identical at runtime

### Runtime Efficiency
- The app must remain extremely lightweight
- Runtime behavior must avoid unnecessary redraws, timers, image decoding, or texture churn
- Heavy work should happen at **build time** or **asset import time**, not continuously at runtime

### Dock Awareness
- The pet must move relative to the **actual detected Dock geometry**
- Movement may not assume the default Dock size
- Dock size/orientation changes should update the valid movement region

### Maintainability
- Adding or updating a pet should not require Swift code changes
- Art pipeline rules must stay simple enough for manual asset creation

---

## Performance Budgets

These are the target budgets for this roadmap update.

### Runtime Memory
- **Primary target:** steady-state memory usage **<= 30 MB**
- Applies to a normal single-pet session after launch stabilization
- No unbounded memory growth over long runs

### CPU
- **Idle target:** <= **0.3%**
- **Typical animated/walking target:** <= **1.0%**
- Short spikes are acceptable only during startup, pet switch, or asset load

### GPU
- No constant heavy GPU work
- No unnecessary offscreen compositing or layer effects
- No continuous texture upload churn
- Rendering path should be simple enough that GPU impact is negligible in practice

### Distribution Size
- Keep packaged release reasonably small
- If a tradeoff exists, **runtime memory and visual fidelity take priority over DMG size**
- Asset pipeline should still avoid wasteful duplication

---

## Guiding Technical Principles

1. **Build-time heavy, runtime light**
2. **One active pet in memory**
3. **Data-driven asset loading**
4. **Integer-only pixel scaling**
5. **Event-driven updates where possible**
6. **No polling if a callback/notification can be used instead**
7. **Precompute where cheaper than recompute**
8. **Do not sacrifice art quality for convenience**
9. **Do not sacrifice maintainability for micro-optimizations too early**
10. **Profile before replacing working subsystems**

## M15 — Asset Pipeline V2 & Source Art Contract

**Status:** `NOT_STARTED`

**Objective:**  
Define the final asset contract so owner-created pixel-art pets can be added consistently without Swift code changes.

**Deliverables:**
- Updated asset pipeline documentation (`docs/ASSET_PIPELINE.md` or a new companion doc)
- Source asset convention for manually created pets
- Folder structure for each pet
- Manifest schema update to support sprite-sheet workflows
- Documentation for:
  - canvas size
  - frame size
  - transparent background rules
  - naming rules
  - state mapping
  - animation FPS
  - anchor / baseline rules
  - scale compatibility rules
- Clear rule for handling:
  - single large sprite sheet
  - per-state sprite sheet
  - per-frame individual PNG files

**Recommended Asset Contract:**
- `source/` folder for original owner-authored files
- `runtime/` or generated output folder for optimized runtime assets
- `manifest.json` stores animation/state metadata
- Each pet may define:
  - `idle`
  - `walk`
  - `interaction`
  - future optional states such as `sleep`, `run`, `special`
- Manifest must support:
  - frame rectangle definitions or grid slicing rules
  - per-state frame order
  - per-state FPS
  - loop/non-loop flag
  - logical pet baseline

**Prerequisites:** M14 `DONE`.

**Definition of Done:**
- A complete written asset contract exists
- A manually created pet can be described entirely through assets + manifest
- No Swift code changes are needed when introducing a new compliant pet
- Asset contract covers both the “many frames in one sheet” case and simpler per-file frame cases

**Risks:**
- Overdesign may make the asset pipeline hard to use
- Under-design may force later code exceptions

**Tests Required:**
- Manual review of asset contract
- Example manifest created for one pilot pet (Cat)
- Dry run: confirm the contract is enough to express a full cat animation set

## M16 — Sprite Sheet Slicing & Build-Time Asset Compilation

**Status:** `NOT_STARTED`

**Objective:**  
Create a build-time or import-time pipeline that can take owner-created sprite sheets and convert them into runtime-ready assets with no quality loss.

**Deliverables:**
- Asset import/slicing script(s), e.g.:
  - `scripts/slice_spritesheet.py`
  - or equivalent Swift utility if preferred
- Grid-based slicing support
- Explicit rectangle-based slicing support
- Optional atlas generation for runtime efficiency
- Metadata generation from source sheet to runtime manifest
- Validation script to catch:
  - inconsistent frame sizes
  - missing states
  - invalid JSON
  - duplicate frame IDs
  - out-of-bounds slice rectangles
- Optional frame deduplication for identical frames
- Build output format optimized for runtime loading

**Important Rule:**
- All expensive slicing/organization work should happen **before runtime**
- Runtime should load already-prepared assets whenever possible

**Prerequisites:** M15 `DONE`.

**Definition of Done:**
- The sample manually created cat sheet can be sliced successfully
- Frames can be mapped into animation states without manual code edits
- Output assets preserve exact source pixels
- Invalid asset definitions fail with clear validation messages
- Pipeline supports “many manually created frames in one sheet” cleanly

**Risks:**
- Atlas packing can introduce sampling artifacts if padding rules are wrong
- Overcompression may damage quality

**Tests Required:**
- Unit/integration: slicing correctness from known coordinates
- Visual regression: compare sliced output vs source
- Manual: import a real owner-created sheet and preview generated frames
- Manual: validate one intentionally broken asset pack and confirm helpful failure output

## M17 — Pixel-Perfect Rendering Hardening

**Status:** `NOT_STARTED`

**Objective:**  
Guarantee that manually created pixel art is rendered at runtime with zero blur and zero visible degradation.

**Deliverables:**
- Rendering audit of the current runtime path
- Explicit nearest-neighbor / no-smoothing configuration at all relevant layers
- Integer-only scale enforcement
- Pixel-grid alignment rules for pet position and sprite origin
- Safe atlas padding/margin rules if atlases are used
- Retina verification strategy
- Optional pre-rendered variants for common scale levels if that reduces runtime cost without harming fidelity
- Written rendering rules documenting what is allowed and forbidden

**Rendering Requirements:**
- No fractional sprite scale
- No subpixel placement that causes shimmer
- No bilinear interpolation
- No mipmapping or dynamic filtering unless proven harmless
- Any “extra render” or preprocessing must happen without altering visible pixels

**Prerequisites:** M16 `DONE`.

**Definition of Done:**
- Pilot pet renders crisply at all supported sizes
- Pixel edges remain sharp on Retina and non-Retina displays
- No shimmer from half-pixel positioning during movement
- Visual output matches source art closely enough that zoomed comparison reveals no unacceptable degradation

**Risks:**
- Core Animation / image-loading defaults may introduce smoothing if not fully controlled
- Atlas edge bleeding may appear if padding is wrong

**Tests Required:**
- Visual snapshot tests at 1x / 2x / 3x
- Manual 400%-800% zoom inspection of screenshots
- Manual movement test to confirm no shimmer during walking
- Manual multi-size test via existing size settings

## M18 — Dynamic Dock Geometry & Movement Region

**Status:** `NOT_STARTED`

**Objective:**  
Make the pet move relative to the actual current Dock geometry and size instead of a default/static Dock assumption.

**Deliverables:**
- Dock thickness inference improvements
- Accurate movement region calculation based on:
  - Dock orientation
  - Dock thickness
  - Dock screen
  - visible movement range above the Dock
- Dynamic reaction to Dock changes:
  - orientation changes
  - size changes
  - screen changes
  - auto-hide changes
- Window/pet repositioning logic updated to use measured geometry
- Fallback strategy when exact Dock size cannot be known via public APIs
- Documentation of what is inferred vs guaranteed

**Implementation Notes:**
- Use public APIs only
- Prefer inference from `screen.frame` vs `visibleFrame`
- If auto-hide prevents direct thickness inference, use the best safe fallback strategy
- Movement bounds must track the real usable path above the Dock as closely as practical

**Prerequisites:** M15 `DONE`.

**Definition of Done:**
- Pet movement path visibly follows the actual Dock region
- Changing Dock size changes the effective movement region without restart
- Left / right / bottom Dock orientations remain supported
- Multi-monitor behavior remains correct
- Auto-hide remains gracefully handled

**Risks:**
- macOS provides no perfect public Dock rect API
- Auto-hide and animation timing may make exact geometry hard to capture

**Tests Required:**
- Manual: Dock size small / medium / large
- Manual: Dock bottom / left / right
- Manual: Dock auto-hide on / off
- Manual: screen attach/detach and multi-monitor scenarios
- Unit: geometry calculations for inferred movement region

## M19 — Runtime Optimization & Memory Budget Reduction

**Status:** `NOT_STARTED`

**Objective:**  
Reduce runtime overhead aggressively so the app remains nearly invisible in CPU/RAM/GPU usage while preserving visual quality.

**Deliverables:**
- Profiling pass with Instruments / Activity Monitor / `ps`
- Memory audit of current asset loading strategy
- Lazy loading for the active pet only
- Unload/release previous pet assets on pet switch where safe
- Avoid duplicate decoded image storage
- Animation scheduling optimization:
  - lower wakeups
  - no redundant timers
  - no redraw if frame/state did not change
- Redraw throttling or frame pacing appropriate for pixel pets
- Event-driven geometry updates instead of polling
- Optional pause/reduce activity when:
  - screen asleep
  - session inactive
  - pet fully static and no frame change needed
- Documentation of achieved runtime budgets

**Optimization Policy:**
- First optimize image lifecycle
- Then redraw frequency
- Then timer behavior
- Replace rendering subsystem only if measurement proves it necessary

**Prerequisites:** M17 `DONE`, M18 `DONE`.

**Definition of Done:**
- Steady-state memory reaches **<= 30 MB target** or a clearly documented closest measured result with explanation
- Idle CPU is at or below target budget
- Walking/normal activity remains within target budget
- No continuous memory growth over long runs
- App remains smooth and visually correct after optimization

**Risks:**
- Some framework baseline memory cost may be hard to reduce below a certain point
- Over-optimization may complicate code or hurt maintainability

**Tests Required:**
- Performance: cold launch memory measurement
- Performance: 5-minute stabilization memory measurement
- Performance: 1-hour and 8-hour soak memory measurement
- Performance: idle CPU measurement
- Performance: active walking CPU measurement
- Manual: verify no visual regressions after optimization

## Notes

When a tradeoff appears between:
1. visual fidelity,
2. runtime efficiency,
3. implementation complexity,

the priority order is:

1. **Visual fidelity must not be broken**
2. **Runtime efficiency should be aggressively optimized**
3. **Implementation complexity should remain manageable**

Heavy work should always be pushed toward **build/import time** instead of **runtime** whenever possible.
